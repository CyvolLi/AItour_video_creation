# 微信小店与云环境修复设计

## 背景

项目当前存在两个相互独立的问题：

1. `app.js` 写死的云环境 `cloudbase-d2g8dvtluc8d8face` 不存在，导致启动时调用 `quickstartFunctions` 返回 `-501000 Environment not found`。
2. `store-product` 已被基础库识别，但微信侧获取商品数据失败。现有页面只渲染商品组件，无法区分小店 AppID、商品 ID、商品状态与桌面调试环境问题。

已确认的有效云环境为 `cloud1-5g34ybsmbfe89727`。小店 AppID 为 `wxde7b459287c6bc1b`，当前测试商品 ID 为 `10001033506602`。

## 方案

采用“集中配置 + 分层诊断”：

- 新建运行配置模块，集中保存云环境、小店 AppID 和测试商品 ID，并生成云初始化参数。
- `app.js` 从配置模块读取有效云环境。OpenID 获取失败仍由现有 Promise 错误处理捕获，不阻塞页面渲染。
- `pages/adver` 同时渲染 `store-home` 与最小参数的 `store-product`：
  - 两者都失败，重点检查小店 AppID、店铺状态或运行平台。
  - `store-home` 成功但 `store-product` 失败，重点检查商品 ID、归属和上下架状态。
  - 开发者工具失败但手机真机成功，判定为桌面调试能力差异。
- 页面展示运行平台、基础库版本、组件能力检测结果和商品跳转回调。组件首次加载不使用自定义样式，以排除非必要变量。
- `pages/navigate` 保留为普通小程序跳转对照，并明确说明它不是微信小店商品组件的替代方案。

## 数据流

1. 小程序启动后，`app.js` 读取运行配置并调用 `wx.cloud.init`。
2. `getOpenId` 调用目标环境中的 `quickstartFunctions`。如果函数未部署，页面继续运行并在控制台输出明确错误。
3. 广告诊断页从同一配置读取小店和商品参数。
4. 微信基础库分别向小店服务请求店铺卡和商品卡数据。
5. 页面根据组件可见性、控制台中的组件名称及跳转回调定位失败层级。

## 错误处理

- 配置模块提供校验，拒绝空云环境、非 `wx` 前缀小店 AppID 和空商品 ID。
- 云函数错误保持非阻塞，避免与小店组件错误混淆。
- 商品跳转失败时在页面和控制台同时记录 `event.detail.code` 与 `message`。
- 桌面平台显示真机验证提示，不把开发者工具结果直接认定为线上结果。

## 测试与验收

- Node 自动测试验证运行配置和云初始化参数。
- 运行已有测试，避免配置调整影响其他工具模块。
- 对全部 JavaScript 和 JSON 做静态语法检查。
- 开发者工具重新编译后确认不再出现 `Environment not found`；若云函数不存在，则按环境重新部署。
- Android、iOS 或鸿蒙真机预览，确认 `store-home` 与 `store-product` 的实际渲染情况。

## 限制

微信小店数据由微信远端服务返回，本地自动测试无法证明指定商品当前处于可售状态。最终商品卡验收必须在手机微信真机完成。
